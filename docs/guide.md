## 書き方の決まり

README は、人が読む最低限だけを書きます。ルートの README の詳細（命名規則、書き方のルール、やってはいけないこと、手順の詳細、チェックリスト、図の書き方の細則）は、このページに置きます。ほかの README で AI向けの補足を書くときは、`<details>` に入れて閉じます。`summary` は `AI向け：` で始めます。GitHub では `summary` のあと空行が必要です。MkDocs では `<details markdown>` を使い、`md_in_html` を有効にします。

見出し `##` が2つ以上あるドキュメントは、冒頭（`#` のタイトルとリード文の直後）に「目次」の節を置きます。目次は `python3 scripts/update-toc.py` で作り直します。手で書きません。

### 深さのルール

| 深さ | 何を書くか | 図 | 例 |
| --- | --- | --- | --- |
| 1 業務 | 誰が何を渡し、仕事がどこまで進むか | PlantUML のスイムレーン | 利用者が公開し、APIが公開中にする |
| 2 機能 | 画面とAPIのつながり | PlantUML のシーケンス図 | 画面が `POST /profiles/{id}/publish` を呼ぶ |
| 3 サービスメソッド | 1つの目的を持つ処理（手順） | `flow.puml` のアクティビティ図 | 持ち主 かつ 本人確認済みかを検証する |

深さ3の文は、次の形にします。

> 公開中にする処理。見ている人にプロフィールを見せるのが目的。

`if` の中の式や、SQLの1行は書きません。メソッド名やコードのパスも書きません。細かい判定は実装に任せます。

### APIと処理詳細の書き方

APIの名前は「名詞＋API」にします（例：商品詳細取得API、支払いAPI）。入口と設計書のタイトル（`#`）、`mkdocs.yml` の nav、図の `title`、ほかのページからのリンクの文字を、この名前にそろえます。「（設計書）」のような付け足しはしません。フォルダ名とファイル名（例: `apis/get-product/`）は、この名前とは別で、変えません。

APIの設計書は `apis/<名前>/処理詳細.md` の1本です。入口の `README.md` は、「何をするか」1行と、設計書・変更履歴へのリンク2行だけにします。設計書と重なってよいのは、この1行だけです。設計書は、次の順で書きます。

1. 概要（何をするかを1文）
2. 説明（呼ぶ人、決めたこと、使う言葉と関連リンク）
3. エンドポイント
4. メソッド
5. リクエスト例（項目の表と curl）
6. レスポンス例（成功と主な失敗の JSON）
7. 処理フローの図（入口の図と、処理のイメージ）
8. 処理詳細（番号の手順）

設計書には、その API の中身だけを書きます。「どこが正か」「この節の読み方」「AI向けの補足」のような、読み方や書き方の説明は設計書に書かず、このページに置きます。

1つのAPIに呼び出しが2つ以上あるとき（例: チャレンジを受け取ってから署名を送る、登録と削除）も、設計書は1本にします。

- エンドポイントは、呼ぶ順に番号を付けて並べる。メソッドが呼び出しごとに違うときは、エンドポイントとメソッドの表にする。
- リクエスト例の項目は1つの表にまとめ、一部の呼び出しだけで要る項目は △ に呼び出しを書く。例: `△（POST /passkeys の場合）`。curl は呼ぶ順に並べる。
- 処理詳細の手順の番号は通しで付け、見出しのすぐ下に「`POST /passkeys` の手順です。」のように、どの呼び出しの手順かを書く。全部の呼び出しで同じ手順（例: セッション検証）は、合う場合の結果に、呼び出しごとの次の手順を書く。

言葉は、APIごとのファイルを作らず、[用語集](../用語集.md) に1か所でまとめます。設計書の説明には「このAPIで使う言葉（利用者、セッション）は、用語集にあります。」のように、使う言葉の名前だけを書きます。エラーコードの意味は、処理詳細の手順とレスポンス例に書きます。

失敗を返さないAPIは、レスポンス例に「失敗のレスポンスはありません」と書きます。

リクエスト例の項目の表の「必須」列は、記号で書きます。凡例「○＝必須、△＝条件付き必須、−＝任意」は、表の上に1回だけ置きます。

- ○: いつも必要
- △: 条件付きで必要。条件を横に書き切る。例: `△（支払い方法がカードの場合）`
- −: 無くてもよい

× は使いません。無いと `400` になる場合は、○ か △ にします。

処理詳細は、`### 1. リクエストバリデーション` のような番号の手順にします。各手順で、何と何を照合するかを書き、「N.M …の場合」に分けて、その下に4スペース下げて結果（返すステータスとエラーコード、保存・削除、次に進む手順）を書きます。対応メソッドとコードのパスは、手順に書きません。メソッド名は、図にも書きません。メソッドの中の細かい分岐は書きません。

```markdown
- 1.1 本文のすべての項目が、手順1の条件に合う場合
    - 手順2へ進む
- 1.2 本文のいずれかの項目が、手順1の条件に合わない場合
    - 400 エラー（`INVALID_REQUEST`）を返す
    - 何も保存しない
```

条件と結果、保存・削除は、この番号の手順が正です。失敗の表は別に作りません。レスポンス例は、どの手順の結果かを番号で示し、条件は書き直しません。バリデーションは、項目ごとの条件を手順1に並べ、リクエスト例の項目の表には書きません。レスポンス例の本文の形は例として書きます。処理フローの図の箱にも、同じ番号を付けます。処理のイメージはスイムレーンにせず、分岐が分かるアクティビティ図にします。

手順の中は、ネストしたリストで段を付けます。見出しの下に、照合する条件と「1.1 …の場合」を1段目に、返すエラー、保存するもの、「手順2へ進む」をその下の2段目に書きます。

「N.M …の場合」と図の分岐の条件には、何が何と合う／合わないかを、主語を付けて書きます。

<details markdown>
<summary>AI向け：条件の主語の例</summary>

| 前 | 後 |
| --- | --- |
| 合わず、連続4回以下の場合 | 入力パスワードが保存済みのハッシュと合わない かつ この失敗でそのメールアドレスの連続失敗が例：4回以下の場合 |
| ロック中の場合 | そのメールアドレスがロック中（例：連続5回失敗から15分以内）の場合 |
| 送信できた場合 | メール送信サービスがログイン通知メールを受け付けた場合 |
| 200 の場合 | 外部APIの返事のHTTPステータスが 200 の場合 |

- 条件を重ねるときは、前後にスペースを空けて「A かつ B」「A または B」と書き、「場合」は最後に1回だけ書く。読点の「、かつ」「、または」、「〜場合で、〜場合」、「合わず」は使わない。図では `A\nかつ B` のように、「かつ」「または」の前で改行する。
- 文と図（flow.puml の if・elseif・else、入口.puml の alt・else）で、同じ条件は同じ言葉にする。
- 図のラベルが長いときは `\n` で改行する。図の分岐ラベルは主語を短くしてよい（例: 「3.1 入力パスワードが\n保存済みのハッシュと合う場合」）。
- レスポンス例の見出しも、同じ主語で書く。

</details>

外部APIを呼ぶ手順には、送る相手、タイムアウト、再試行の回数、失敗時に返すステータスとエラーコード、保存するものの5つを表で書きます。表が正です。外部APIの返事のHTTPステータスごとの分かれ方（例: HTTPステータスが 200 なら次へ、404 なら 404 エラー、それ以外なら 503 エラー）は「N.M …の場合」で書きます。処理フローの図では、外部APIを薄い青の箱（`外部API：名前` と役割1行）にし、横の付箋にはタイムアウト・再試行・失敗時の3つだけを書きます。送る相手と保存するものは、表だけに書きます。1回の呼び出しは、箱1つにします。決まっていない数字には「例：」を付けます。

この形は、[ログインAPI](../apis/login/処理詳細.md) と `apis/_template` だけです。ほかのAPIは、まだ前の形（処理詳細に「入力と結果」「失敗するとき」の表がある形）です。

<details markdown>
<summary>AI向け：段の付け方</summary>

- 2段目は4スペースで字下げする。MkDocs は2スペースでは入れ子にならない。
- 次の手順は「手順2へ進む」と書く。行頭を「2. 」にすると番号付きリストになるため。`\` で逃がす書き方は使わない。
- 外部APIの表は、説明の項目の下に4スペース字下げで置き、前後に空行を入れる。GitHub と MkDocs のどちらでも、リストの中の表として表示される。
- 見出し（`### 1. …`）は字下げしない。

</details>

### やってはいけないこと

- 深さ3より細かいロジックを、設計書に写さない。
- 図の中身を、PlantUML.com や Kroki に送らない。
- 図に Mermaid を使わない。PlantUML で書き、SVG を Markdown から参照する。
- PlantUML で URL を `!include` しない。アイコンは jar 同梱の `<awslib/...>` を使う。
- PRタイトルを `fix` や `feat:` にしない。何をどう変えたかを日本語で書きます。例: `公開時に本人確認を追加`。
- draw.io を変えたのに、変更前と変更後のスクリーンショットを貼らない。
- PR本文の「概要」を3行以上にしない。補足や具体例は、閉じた details に入れる。

### 構成図（PlantUML）の書き方

インフラ構成図は PlantUML と awslib のアイコンで書きます。記入例は [AWSのインフラ構成](infra/index.md) です。

箱の中には、名前と概要・役割を1行書きます。詳しい補足と具体例は、黄色い付箋に書きます。付箋は対象の箱の真横（または真下）に置き、短い点線でつなぎます。付箋は、対象と同じ枠の内側に置きます。枠をまたぎません。矢印は交差させません。

例です。箱は `ElastiCache プライマリ（1a）／セッションを置く`、付箋は `どのAPIでもログインが続く` です。NAT と ALB も、箱の中に役割を1行書きます。

### draw.io を使うとき

draw.io の差分は、レビューで追いにくいです。使う場合は次の2つを守ります。

- `.drawio` ファイルもリポジトリに入れる。
- PRに、変更前と変更後のスクリーンショットを貼る。

PlantUML で足りる図は、draw.io にしません。

## 新しいAPIと業務フローを足す手順

`apis/_template` をコピーして、中身を埋めます。

```bash
cp -a apis/_template apis/予約を確定する
```

コピーした `変更履歴.md` は、「# 変更履歴」の1行だけのままにします。

記入例は [プロフィール公開API](../apis/publish-profile/README.md) です。本人確認が済んでいる人だけ、プロフィールを公開中にします。

ほかの記入例は、[ログインAPI](../apis/login/README.md)、[ログアウトAPI](../apis/logout/README.md)、[商品詳細取得API](../apis/get-product/README.md)、[商品一覧取得API](../apis/list-products/README.md)、[商品検索API](../apis/search-products/README.md)、[パスキー登録API](../apis/register-passkey/README.md)、[パスキーログインAPI](../apis/login-passkey/README.md)、[アカウント復旧API](../apis/recover-account/README.md)、[カード登録API](../apis/register-card/README.md)、[支払いAPI](../apis/create-payment/README.md)、[注文状態取得API](../apis/get-order/README.md)、[決済通知受信API](../apis/payment-webhook/README.md) です。業務フローの記入例は、[ログインして商品を探す](business/ログインして商品を探す/README.md)、[カードで支払う](business/カードで支払う/README.md)、[パスキーの端末をなくす](business/パスキーの端末をなくす/README.md) です。

新しい業務フローを足すときは、既存のフォルダをコピーして、中身を書き換えます。

```bash
cp -a docs/business/プロフィールを公開する docs/business/予約を確定する
```

コピーした `変更履歴.md` は、「# 変更履歴」の1行だけに戻し、コピー元の履歴の行は消します。`mkdocs.yml` の nav に、新しいフォルダの README と変更履歴を追加します。フォルダ名に `/` は使いません。パスが壊れるためです。

## 図の変換とローカルプレビュー

図は、自分のマシンと GitHub Actions の中だけで変換します。PlantUML.com や Kroki には、図の中身を送りません。

### 1. 変換ツールを入れる

Java と Graphviz が必要です。日本語の図には、Noto CJK フォントがあると字形が揃います。

Ubuntu / Debian:

```bash
sudo apt-get install -y default-jre-headless graphviz fonts-noto-cjk
./scripts/install-plantuml.sh
```

macOS:

```bash
brew install --cask temurin
brew install graphviz
./scripts/install-plantuml.sh
```

`scripts/install-plantuml.sh` は、PlantUML 1.2026.10 の jar を `tools/plantuml.jar` に置きます。ダウンロードするのは変換ツールだけで、図のテキストは送りません。

SVGにするときは、次を実行します。

```bash
./scripts/render-puml.sh docs/business/プロフィールを公開する/flow.puml
```

`.svg` は `.puml` と同じ場所に置きます。

### 2. VS Code / Cursor で見る

推奨拡張は `.vscode/extensions.json` に書いてあります。

- PlantUML（`jebbs.plantuml`）
- Markdown Preview Enhanced（`shd101wyy.markdown-preview-enhanced`）

ワークスペース設定で、プレビューはローカル変換です。

- `plantuml.render` は `Local`、`plantuml.server` は空です。`.puml` を開いて `Alt+D`（Mac は `Option+D`）でプレビューします。
- Markdown Preview Enhanced の `plantumlServer` も空です。空のときだけ、`tools/plantuml.jar` を使います。ここに URL を書くと、図の中身がそのサーバーへ送られます。
- jar が見つからないときは、`markdown-preview-enhanced.plantumlJarPath` を `tools/plantuml.jar` の絶対パスに変えます。`scripts/install-plantuml.sh` が絶対パスを表示します。
- Kroki と WebSequenceDiagrams の送信先は `127.0.0.1:9` にしてあります。この2つの記法は使いません。

### 3. mkdocs serve で見る

サイトは MkDocs Material です。PlantUML から作った SVG を表示します。図を押すと、拡大できる窓が開きます。検索は日本語です。

<details markdown>
<summary>AI向け：図の拡大窓</summary>

- 実装は `javascripts/image-zoom.js` と `stylesheets/extra.css`。`mkdocs.yml` の `extra_javascript` と `extra_css` で読み込む。`scripts/prepare-docs.sh` が `mkdocs/docs/javascripts` へのリンクを作る。
- 本文の `.md-typeset img` だけを対象にする。図を別の要素で包まない（PDF の図の扱いが変わるため）。
- 窓は開くまで DOM に作らず、閉じたら消す。PDF 生成はページ内のすべての `img` を検証するため。印刷では CSS で隠す。
- 大きな SVG は、同じサイト（同一オリジン）のものだけを取得してインラインで拡大する。違う場所のファイルは取得しない。`img` のビットマップを引き伸ばさない。
- ホイール、ピンチ、ドラッグ、画面の＋／−、Esc、背景クリック、閉じるボタン、`+` / `-` / `0`、矢印キーに対応する。図の上をクリックしても窓は閉じない。

</details>

```bash
python3 -m venv .venv
source .venv/bin/activate   # Windows は .venv\Scripts\activate
pip install -r requirements.txt
NO_MKDOCS_2_WARNING=1 mkdocs serve -a 127.0.0.1:8765
```

ブラウザで <http://127.0.0.1:8765> を開きます。`NO_MKDOCS_2_WARNING=1 mkdocs build --strict` で、リンク切れも確認できます。結果は `site/` に出ます。

MkDocs は、設定ファイルのあるフォルダ自体を原稿フォルダにできません。そのため `mkdocs/docs` から、このリポジトリの原稿へリンクしています。リンクが無いときや、Windows でリンクが実体にならないときは、`./scripts/prepare-docs.sh` を実行します。

Material for MkDocs は 2027-05-05 まで保守されます。起動時の案内は、上の環境変数で消せます。

## PDF にする

まとめて渡すときは、PDF にします。1つのコマンドで、`pdf/` に次の PDF を作ります。`pdf/` はコミットしません。

| ファイル | 中身 |
| --- | --- |
| `pdf/設計書.pdf` | サイトのページをまとめたもの。`_template` の型、各変更履歴、このページ（AI向け）、GitHub の設定は入れない。先頭の目次とPDFのしおりから、各ページへ飛べる |
| `pdf/apis/<名前>.pdf` | APIごとの `処理詳細.md` |
| `pdf/業務フロー/<業務>.pdf` | 業務フローごとの README |

```bash
source .venv/bin/activate
pip install -r requirements.txt -r requirements-pdf.txt
python -m playwright install chromium   # 初回だけ。Linux で足りないライブラリがあるときは --with-deps を付ける
./scripts/render-changed.sh --all       # .puml を変えたときだけ。図の SVG を作り直す
./scripts/build-pdf.sh
```

- MkDocs のサイトを作り、ヘッドレスの Chromium で印刷します。見た目はサイトと同じで、ヘッダー、ナビゲーション、検索、フッター、コピーボタンを消します。下にページ番号が入ります。
- 日本語のフォントに Noto Sans CJK JP を使います。Linux では `fonts-noto-cjk` を入れます。
- 図は、手元にある SVG を使います。Actions では、毎回 `.puml` から SVG を作り直してから PDF にします。
- 図が欠けているとき（`mkdocs build --strict` の警告や、読み込めない画像）は、PDF を作らずに失敗します。
- PDF には、人が読む内容だけを入れます。このページ（`docs/guide.md`）、GitHub の設定（`docs/setup.md`）、summary が「AI向け：」で始まる details は入れません。この2ページへのリンクも消します。
- A4 縦の幅と高さに収めると 75% より小さくなる図は、図の大きさに合わせた用紙の1ページに、等倍で載せます。図の直前の見出しと導入文も、そのページの図の上に載せます。見出しが無いときは、ページと節の名前に「（つづき）」を付けて入れます。本文は A4 縦のままです。大きい図のページは画面で拡大して見ます。印刷するときは「用紙に合わせる」にします。「カードで支払う」の業務フローの図のページは 1771×1823mm（A0 より大きい）で、ふつうの用紙には読める大きさで印刷できません。
- 文書の最後（図だけのページの前も）で、数行だけが次のページにはみ出すときは、その文書だけ字を少し小さく（10pt か 9.5pt）して、前のページに収めます。
- A4 の本文に載せる図で、前のページが大きく空くときは、図を少し縮めるか、文字の無い行で図を分けて詰めます。
- PDF の中に無いページや `.puml` へのリンクは、GitHub のファイルを指します。

## 自動化

| いつ | 何をする |
| --- | --- |
| `main` 以外のブランチへ `.puml` を push したとき | Actions の中で SVG に変換し、同じ場所へコミットする。`main` は直接 push を禁止しているので、SVG は PR のブランチで作る |
| PRで図が変わったとき | 変わった図を PR コメントに出す。追記と修正は「### 追記した図：パス」「### 修正した図：パス」の見出しの下に、変換した SVG を閉じずに画像で載せる。消した図は、最後の「### 削除した図」にパスだけ並べる。PRで足した・変えた部分は赤く描き、消したものは図の下に文字で並べる（`PREVIEW_TOKEN` が無いときはリンクだけで、色は付かない）。説明文は出さない。図は Actions の中だけで SVG にし、外部のサーバーへ送らない。コメントに画像が出ないときは、各図の「SVGを開く」から開く。SVG は一覧に出さず、元の `.puml` のパスで出す。リネームは削除と追記として出す。PNG は、その実行のアーティファクト `plantuml-png` にあり、Actions の実行ページから開く |
| PRを開いた・push したとき | 変わったドキュメント（`.md`、`.puml`）を「追記ドキュメント」「修正ドキュメント」「削除ドキュメント」に分けて、PR コメントと Job Summary に出す。追記と修正は公開ページへのリンク、削除はリンクなしのパス、無いときは「なし」。SVG と `変更履歴.md` は出さない。リネームは削除と追記として出す。リンク先は公開サイト（main を公開したページ）で、マージして公開されるまでは、追記したページは開けず、修正したページは前の内容。コメントは、先頭の「## 変更したドキュメント」と、その下の3つの見出し（###）と一覧だけ |
| `main` へマージしたとき | 変わった `apis/<名前>/変更履歴.md` と `docs/business/<業務>/変更履歴.md` の、マージした日の見出しの下に1行足す。マージした PR は、push されたコミットから探す。`main` へは、ルールの例外にしたデプロイキー（Secret `CHANGELOG_DEPLOY_KEY`）で push し、その push でサイトが公開し直される。同じ3つの分類の一覧を Job Summary に出す |
| `main` へ push したとき、または手動で実行したとき | `.puml` から SVG を作り直し、`scripts/build-pdf.sh` で PDF を作り、アーティファクト `design-doc-pdf` に置く（30日）。Pages の設定に関係なく動く。PDF を作る仕組み（`scripts/build-pdf.*`、`requirements-pdf.txt`、`pdf.yml`）を変えた PR でも作って検証する |
| `main` へ push したとき、または手動で実行したとき | MkDocs Material を GitHub Pages へ公開する。Pages が使えないときは、公開を飛ばさずジョブを失敗にする |
| PRを開いた・push したとき | `scripts/update-toc.py --check` で、目次が見出しとずれていないかを検証する。ずれていたら失敗し、直すコマンドを出す |
| PRを開いた・push したとき | gitleaks で、PR のコミットにトークンや鍵が無いかを探す。見つかったら失敗する。ドキュメントのダミー値の例外は `.gitleaks.toml` に、値ごとに書く |
| PRを開いた・タイトルを変えたとき | タイトルが日本語で、`fix` などの接頭辞でないことを確認する |
| PRを開いた・本文を変えた・push した・開き直したとき | ベースブランチの `scripts/check-pr-body.py` で本文の形を検証する。「## 概要」より前はコメントと空行だけ、「## 概要」（## だけ）がコメントと空行を除いて1〜2行、「## 判断してほしい点」が番号付きの行か「なし」、それより後は閉じた details の中だけ（外は空行・コメントと、details が続く見出しのみ）、details に `open` 属性が無いこと。テンプレートのままは失敗。bot（user.type が Bot）が作るPRは対象外 |

PRコメントの赤い図は、`scripts/highlight-puml-diff.py` が作ります。比較元のブランチと PR の `.puml` を行ごとに比べ、足した・変えた行に色の指定を付けた一時コピーを、Actions の中で SVG にします。リポジトリにコミットする SVG は、ふだんの色のままです。

| 行の種類 | コメントの図でどうなるか |
| --- | --- |
| アクティビティ `:処理;`（複数行も） | 背景を薄い赤、枠を赤くする |
| 分岐・繰り返し `if` `elseif` `while` `repeat while` `switch` | ひし形を薄い赤にする |
| ノート `note right: …`、`note … end note` | ノートを薄い赤にする |
| 矢印 `-> ラベル;`、`A -> B : メッセージ` | 線とラベルを赤くする |
| 要素の宣言 `participant` `class` `component` など | 背景を薄い赤にする。クラスの中の行を変えたときは、クラスごと赤くする |
| `else` `endif` `start` `stop` スイムレーン `skinparam` `title` など | 色を付けない。コメントの「色は付けていませんが、図の形には入っています」に出す |

- 消した行は図に出せないため、「消したもの」として図の下に並べます。変えた行は「変えたもの（前 → 後）」にも出ます。
- 並べ替えただけの行（同じ文が比較元にも PR にもある行）は、足した・変えた・消したにしません。
- 新しい図は全体が新しいため、色を付けません。名前を変えた図も、追記した図と削除した図として扱います。
- 図を消しただけの PR にも、「削除した図」のコメントを付けます。
- `#pink :処理;` のような古い書き方の色は、赤くするときに外します。
- 色を付けると変換できない図は、警告を出して、ふだんの色で載せます。
- Actions の成果物 PNG も、赤くした図です。

SVGのコミットメッセージには `[plantuml-svg]` が付きます。`GITHUB_TOKEN` による push は、次の workflow を起動しません。図の変換が無限に繰り返されないためです。

`apis/<名前>/変更履歴.md` と `docs/business/<業務>/変更履歴.md` は、`main` へマージしたときに自動で行が足されます。人は手で書きません。ファイルの先頭は「# 変更履歴」の1行だけにし、書き方の説明はファイルに書かず、このページだけに置きます。

変更履歴は、日付の見出し（`## YYYY-MM-DD`）の下に、`- [#PR番号](PRのURL) PRタイトル` の箇条書きで並べます。行を並べただけだと、サイトでは1つの段落につながって見えるためです。日付は日本時間です。同じ日の見出しがあれば、その下の最後に1行足します。無ければ、見出しを作ってから足します。見出しの順番は、そのファイルの今の順番（古い順か新しい順か）に合わせます。同じ行は二重に足しません。対象のAPIと業務フローは、マージしたPRが触ったファイルだけを見て決めます。`_template` など、`_` で始まるフォルダは対象外です。以前 main に入った変更は含めません。1行足して main に push できたときだけ、サイト公開のワークフローを起動します。

```markdown
# 変更履歴

## 2026-11-16

- [#12](https://github.com/<owner>/<repo>/pull/12) 公開時に本人確認を追加
- [#13](https://github.com/<owner>/<repo>/pull/13) ロックの期間を書き足す
```

各行は、PR番号からそのPRへのリンクにします。PRのURLは、ワークフローの `GITHUB_SERVER_URL` と `GITHUB_REPOSITORY` から作ります。無いとき（手元で動かすとき）は、`git remote` の origin から作ります。リポジトリ名はスクリプトに書きません。同じPR番号とタイトルの行があれば、日付が違っても足しません。古い形の行（`2026-11-16 #12 …` や `- #12 …`）が残っていれば、足す前にこの形へ直します。前の形で先頭にあった説明（「`main` へマージすると…」「形式は…」）が残っていれば、足すときに消します。ファイルが無いときは、「# 変更履歴」だけのファイルを作ってから足します。

作業ブランチでは、サイトを公開しません。Pages へ出すのは `main` だけです。公開は、`main` への push か、手動実行で動きます。人がやる GitHub の設定は [GitHub の設定](setup.md) です。
